Week 7 · Part III — the delivery machine

The pipeline & the mini-PCC

Two halves of the same idea: process as data. Skills encode multi-phase workflows as executable documents agents must follow completely; agent sessions make work claims atomic and auditable; and the Process Control Center renders the whole pipeline for the human operator — who acts only at decision points, because the server derives, the UI projects.

  • Concept: skills, phase discipline, premature completion as violation
  • Build: assign_agent / claim_work (atomic) / complete_agent
  • Build: the process HTTP API (Go)
  • Build: a Next.js mini-PCC: journey map + findings console
7.1Skills: process as executable documentsSKILL.md▶

A skill is a markdown file that IS the process: numbered phases, gate checks between them, exact graph mutations per phase, and a defined terminal state. The enforcement doctrine is strict: load the skill before doing anything else, execute every phase, pass every gate, and end by closing your agent session. Premature completion is a process violation even when the output is correct — each phase catches a different failure class, and skipping one ships those failures downstream.

In the real system

.claude/skills/bld-*/SKILL.md — 100+ skills; the ideation funnel alone is bld-ideate (423 lines: forcing questions → similarity check → server-allocated CIR id → content-gated redeem) → bld-challenge (adversarial validation, ≥2 implementation alternatives mandatory) → bld-promote (CIR → formal xDR, with a verify-or-mark contract on every graph write). The binding rule is .claude/rules/bld-skill-enforcement.md; sensitive skills set disable-model-invocation: true so only an explicit slash command can trigger them.

7.2Agent sessions & claiming workclaim_work▶

When multiple builders run in parallel (week 8's waves!), "who is working on what" must be graph state, not vibes. An AgentSession node with a WORKS_ON edge is minted per dispatch; claim_work is an atomic compare-and-set so two builders can never claim the same work package; complete_agent closes the session and refuses a "completed" status without a real summary — the server-side backstop against agents declaring victory on faith.

In the real system

assign_agent mints the session + WORKS_ON edges; claim_work delegates to store.ClaimWork — claim + session creation in one transaction; complete_agent validates the AgentSession transition map and requires a [SESSION_AUDIT_RUN: marker in the result summary before accepting "completed" — a server-side check backing a client-side hook. Completion triggers the responsibility-status rollup recompute.

Tasks

  1. Implement the trio in server/internal/graph/sessions.go:

    server/internal/graph/sessions.go
    package graph

import (
	"fmt"

	"github.com/google/uuid"
)

func (s *Store) AssignAgent(agentType, respID string) (string, error) {
	if _, err := s.GetNode(respID); err != nil {
		return "", err
	}
	id := "session-" + uuid.NewString()
	if err := s.CreateNode(Node{ID: id, Type: "AgentSession", Status: "active",
		Props: map[string]any{"agent_type": agentType}}); err != nil {
		return "", err
	}
	return id, s.CreateEdge(id, respID, EdgeWorksOn)
}

// ClaimWork: atomic compare-and-set. The UPDATE only wins if the WP
// is still NOT_STARTED — rows-affected 0 means someone beat us to it.
func (s *Store) ClaimWork(sessionID, wpID string) (bool, error) {
	res, err := s.db.Exec(`
		UPDATE nodes SET status = 'BUILDING',
		  updated_at = strftime('%Y-%m-%dT%H:%M:%SZ','now')
		WHERE id = ? AND project_id = ? AND type = 'WorkPackage'
		  AND status IN ('NOT_STARTED','SPECIFIED')`,
		wpID, s.projectID)
	if err != nil {
		return false, fmt.Errorf("claim: %w", err)
	}
	n, _ := res.RowsAffected()
	if n == 0 {
		return false, nil // already claimed — not an error, a race lost
	}
	// Record the claim: changelog + WORKS_ON, best-effort but loud.
	s.db.Exec(`INSERT INTO changelog (project_id,node_id,from_status,to_status,reason,at)
		VALUES (?,?,?,?,?,strftime('%Y-%m-%dT%H:%M:%SZ','now'))`,
		s.projectID, wpID, "NOT_STARTED", "BUILDING", "claimed by "+sessionID)
	return true, s.CreateEdge(sessionID, wpID, EdgeWorksOn)
}

func (s *Store) CompleteAgent(sessionID, status, summary string) error {
	if status == "completed" && len(summary) < 40 {
		return fmt.Errorf("summary_required: 'completed' needs a real result "+
			"summary (>=40 chars) — what shipped, what's left, how you verified")
	}
	if status != "completed" && status != "failed" {
		return fmt.Errorf("bad_terminal: completed | failed")
	}
	if err := s.UpdateNode(sessionID, map[string]any{"result_summary": summary}); err != nil {
		return err
	}
	return s.UpdateStatus(sessionID, status, "agent session closed")
}

7.3The process API (HTTP plane)/api/pipeline▶

The PCC doesn't speak MCP — it speaks HTTP. The real UI runs on two data planes (a Go "process server" REST API for computed reads and all mutations; GraphQL for deep relationship walks); your mini needs only the REST plane. The key design rule carries over whole: status→stage mapping is served by the API, not hardcoded in the UI — the server owns the lifecycle's shape.

In the real system

A Go process server on :13000 serves /api/pipeline, /api/lifecycle, /api/findings, /api/health, /api/attention… and all DA mutations; Apollo/Neo4j GraphQL on :4000 serves the deep walks (@relationship directives auto-generate resolvers). The UI is pull-based with push-driven cache invalidation over a /ws/state WebSocket; the Journey Map fetches its stage definitions from /api/lifecycle with a hardcoded fallback.

Tasks

  1. Build the HTTP plane:

    server/internal/httpapi/server.go
    package httpapi

import (
	"encoding/json"
	"net/http"
	"strings"

	"minidde/server/internal/graph"
)

type Stage struct {
	Key      string   `json:"key"`
	Label    string   `json:"label"`
	Statuses []string `json:"statuses"`
}

// The server owns the lifecycle's shape — the UI renders whatever
// this says, so a lifecycle change never needs a frontend deploy.
var Lifecycle = []Stage{
	{Key: "backlog", Label: "Backlog", Statuses: []string{"NOT_STARTED"}},
	{Key: "design", Label: "Design", Statuses: []string{"DESIGNING", "DESIGN_COMPLETE"}},
	{Key: "build", Label: "Build", Statuses: []string{"BUILDING", "BUILT"}},
	{Key: "review", Label: "Review", Statuses: []string{"IN_REVIEW", "FIXING"}},
	{Key: "integrate", Label: "Integrate", Statuses: []string{"INTEGRATING"}},
	{Key: "complete", Label: "Complete", Statuses: []string{"COMPLETE"}},
}

func New(st *graph.Store) http.Handler {
	mux := http.NewServeMux()
	writeJSON := func(w http.ResponseWriter, v any) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(v)
	}

	mux.HandleFunc("GET /api/lifecycle", func(w http.ResponseWriter, r *http.Request) {
		writeJSON(w, Lifecycle)
	})

	mux.HandleFunc("GET /api/pipeline", func(w http.ResponseWriter, r *http.Request) {
		resps, err := st.QueryAll("Responsibility", "")
		if err != nil {
			http.Error(w, err.Error(), 500)
			return
		}
		writeJSON(w, resps)
	})

	mux.HandleFunc("GET /api/findings", func(w http.ResponseWriter, r *http.Request) {
		findings, err := st.QueryAll("Finding", r.URL.Query().Get("status"))
		if err != nil {
			http.Error(w, err.Error(), 500)
			return
		}
		writeJSON(w, findings)
	})

	mux.HandleFunc("GET /api/responsibilities/{id}", func(w http.ResponseWriter, r *http.Request) {
		pkg, err := st.AssembleContext(r.PathValue("id"))
		if err != nil {
			status := 500
			if strings.Contains(err.Error(), "not found") {
				status = 404
			}
			http.Error(w, err.Error(), status)
			return
		}
		writeJSON(w, pkg)
	})

	// The ONE operator mutation of the mini-PCC: resolve a finding.
	mux.HandleFunc("POST /api/findings/{id}/resolve", func(w http.ResponseWriter, r *http.Request) {
		var body struct{ Resolution, VerificationNote string }
		json.NewDecoder(r.Body).Decode(&body)
		if err := st.ResolveFinding(r.PathValue("id"), body.Resolution,
			"decision-authority", body.VerificationNote); err != nil {
			http.Error(w, err.Error(), 422)
			return
		}
		writeJSON(w, map[string]bool{"ok": true})
	})

	return cors(mux)
}

func cors(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Access-Control-Allow-Origin", "http://localhost:3000")
		w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
		w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		if r.Method == http.MethodOptions {
			w.WriteHeader(204)
			return
		}
		next.ServeHTTP(w, r)
	})
}

7.4The mini-PCC (Next.js)journey map▶

The PCC's UX doctrine in three lines: pipeline-as-place (each Responsibility card sits in its lifecycle-stage column — the UI is the process documentation); the server derives, the UI projects (no status computation client-side, ever); and operators act only at decision points (the only writes on screen are DA actions — everything else is read-only observation of agents working). You'll build three screens that carry all three ideas.

In the real system

Rollups (outcomerollup, respstatusrollup) are Go packages — the sole writers of derived status.

    pcc/lib/api.ts
    const API = "http://localhost:13000/api";

export type Node = {
  id: string; type: string; status: string;
  props: Record<string, unknown>;
};
export type Stage = { key: string; label: string; statuses: string[] };

async function get<T>(path: string): Promise<T> {
  const r = await fetch(`${API}${path}`);
  if (!r.ok) throw new Error(`${path}: ${r.status} ${await r.text()}`);
  return r.json();
}

export const api = {
  lifecycle: () => get<Stage[]>("/lifecycle"),
  pipeline: () => get<Node[]>("/pipeline"),
  findings: (status?: string) =>
    get<Node[]>(`/findings${status ? `?status=${status}` : ""}`),
  responsibility: (id: string) => get<unknown>(`/responsibilities/${id}`),
  resolveFinding: (id: string, resolution: string, verificationNote: string) =>
    fetch(`${API}/findings/${id}/resolve`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ Resolution: resolution, VerificationNote: verificationNote }),
    }).then(async (r) => {
      if (!r.ok) throw new Error(await r.text());
    }),
};

    pcc/app/journey.tsx (core shape)
    "use client";
import { useQuery } from "@tanstack/react-query";
import { api, type Node, type Stage } from "@/lib/api";

export default function Journey() {
  const stages = useQuery({ queryKey: ["lifecycle"], queryFn: api.lifecycle });
  const pipeline = useQuery({
    queryKey: ["pipeline"],
    queryFn: api.pipeline,
    refetchInterval: 5000, // the PCC itself polls where freshness matters
  });
  if (!stages.data || !pipeline.data) return <p>Loading pipeline…</p>;

  const inStage = (s: Stage) =>
    pipeline.data.filter((n) => s.statuses.includes(n.status));

  return (
    <div className="grid auto-cols-fr grid-flow-col gap-3 p-4">
      {stages.data.map((s) => (
        <section key={s.key} className="rounded-xl border p-2">
          <h2 className="text-xs font-bold uppercase tracking-wide">
            {s.label} · {inStage(s).length}
          </h2>
          {inStage(s).map((n) => (
            <Card key={n.id} node={n} />
          ))}
        </section>
      ))}
    </div>
  );
}

function Card({ node }: { node: Node }) {
  const eli10 = node.props.eli10 as string | undefined;
  return (
    <a href={`/responsibility/${node.id}`}
       className="mt-2 block rounded-lg border p-2 hover:border-violet-500">
      <p className="text-sm font-semibold">{String(node.props.name ?? node.id)}</p>
      {eli10 ? (
        <p className="mt-1 text-xs opacity-70">{eli10}</p>
      ) : (
        <p className="mt-1 text-xs italic text-amber-600">
          no plain-English summary yet
        </p>
      )}
      <p className="mt-1 font-mono text-[10px] opacity-60">
        {node.status}{node.props.wave ? ` · wave ${node.props.wave}` : ""}
      </p>
    </a>
  );
}

Why it exists

The respstatusrollup engine in the real system can self-heal a lagging Responsibility status from evidence — but it is capped at IN_REVIEW and can never mint COMPLETE, and it no-ops rather than dragging a status down. Derived state has one writer, terminal states stay on the gated path, and the UI renders whatever the server says: this division is what keeps a control panel honest when both humans and agents are mutating the world under it.
