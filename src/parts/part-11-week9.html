9.1Foundation & the build phase machinephases 0→G▶

bld-foundation-build lays the shared base and freezes it; bld-autonomous-build then drives each Responsibility through phases 0→G — and the team lead running it never writes code itself and never believes a subagent. Its core pattern is verify-personally-then-gate: the orchestrator runs the tests, the build, and the stub-scan with its own hands, submits the raw output as gate evidence, and a server-checked gate must pass before any phase advance. Around it, bld-branch-discipline makes 35+ parallel worktrees structurally conflict-free: one worktree = one branch, each Responsibility writes only its own directory, merges land in wave order behind a 7-condition gate.

In the real system

The Foundation Exit gate: zero warnings, all tests green against mocks, every contract has a mock ("NEVER leave any contract without a corresponding mock"), four reviewer verdicts, zero stubs — then commit to main and pkg/ becomes read-only for all of Stage 5. bld-autonomous-build's thresholds are exact: >20% test failures in a wave routes back to the Builder; fewer than 3 findings across 4 reviews of >500 LOC triggers a superficial-review investigation; and Phase G walks the CHILD SESSION LEDGER to complete_agent every minted child — 155+98 zombie "active" sessions were once hand-swept because nobody closed them. bld-branch-discipline: NEVER git checkout inside a worktree (read other branches with git show branch:path); commits are stage(responsibility): description, one per phase. bld-tech-stack-patterns binds every pattern row to its governing ADR so a review finding is a citation, not an opinion.

Tasks

  1. Build the contract→mock generator + foundation gate. A generator that emits a Go struct and a mock publisher per Event/Contract node in your graph, and a foundation_exit gate that refuses the "commit to main" step unless every contract node has a matching mock file on disk and go test ./... passes. After it passes once: declare capstone/pkg/ frozen — your week-10 build honors it.

  2. Wire the phase machine to your gates. You built submit_gate_evidence/check_gate in week 6; now demand three evidence classes on build_exit: tests_pass, compile_clean, no_stubs_detected — each submitted from output YOU generated by running the command, never from a subagent's summary. A missing class blocks the gate; a rejected update_status stops the run loudly.

  3. Adopt worktree discipline. Make your build flow create git worktree add .worktrees/<resp> -b build/<resp> per Responsibility, then add a pre-merge check that diffs the branch against main and fails if any changed path falls outside that Responsibility's directory (your capstone/pkg/ equivalent included). Structural conflict-freedom beats merge-conflict resolution every time.

  4. Write your pattern table. Five rows for your stack (Go + Memgraph + MCP), each citing one of your own mini-ADRs — e.g. "ctx first arg, never stored (ADR-…)", "MERGE for every node write (ADR-memgraph-is-mini-…)". Plant one violation in a diff and have your review step emit a finding naming pattern + ADR.

Checkpoint

foundation_exit blocks while one contract lacks a mock; build_exit demands all three evidence classes; the pre-merge check catches a foreign-directory edit; the planted pattern violation comes back as a citation-carrying finding.

9.2The test estate: verdicts live on the graphBLOCKED ≠ FAILED▶

The test skills share one iron rule: a determination that isn't on the graph didn't happen. bld-test-author writes a scenario and must land its verdict as graph state — PASSED pushes results, FAILED registers a defect Finding with edges, and BLOCKED is an explicit MISSING:<reason> marker plus a BLOCKED_BY edge to the specific prerequisite Finding. bld-test-run's sharpest move is reconciling those edges to proven reality on every run: probe the target before attributing the block. And bld-test-methodology makes test classification mechanical enough to grep.

In the real system

The driver for the determination contract: a triage once classified 672 test cases and published NONE — analysis without graph writes evaporates. The false-green trap: an assertion written {"path":.., "value":..} instead of the real {actual, op, expected} schema passes VACUOUSLY — unknown keys drop silently and expected becomes nil. bld-test-run's probe rule: ANY HTTP status back means the block is a TOKEN prerequisite, not network — DNS failure/timeout means genuinely unreachable; 1–5 retries is normal log-lag, 6+ consecutive failures on the same case is real signal. bld-test-methodology's tautology oracle (pitfall P5): a test was repointed at the exact function the render path calls, going green everywhere while becoming unable to catch a wrong policy — the tell is a test that cannot be made to fail by writing a plausibly WRONG value into production.

Tasks

  1. Add Test nodes with honest assertions. A Test node type whose scenario JSON uses {actual, op, expected} triples — and a validator that REJECTS unknown assertion keys instead of dropping them (the vaccine for the false-green trap). Derive state = "blocked" server-side whenever any env value starts with MISSING:; prove the state flips to runnable when you fill the value.

  2. Build the BLOCKED_BY reconcile. Add the edge type; write /mini-test-run: curl-probe the target URL first — any HTTP status → edge the Test to a "token-missing" prereq Finding; DNS failure/timeout → "network-unreachable". On a green run: delete the satisfied edge, and resolve the prereq Finding when it was the last edge pointing at it. BLOCKED is a legitimate outcome — it must never be flattened into FAILED in your result enum.

  3. Run the methodology greps over your own suite: DB drivers imported in untagged tests, time.Sleep in tests, assertion-free test functions. File one mini-Finding per hit; re-tag (//go:build integration) or fix each. Your unit tier must run green with the Memgraph container STOPPED — that is what the tags buy you.

  4. Kill a tautology. Pick one of your tests and ask: can it fail if I write a plausibly WRONG value into the production path? If not, rewrite it against an independently-authored expectation table — then prove it by planting the wrong value and watching it go red.

Checkpoint

An assertion with an unknown key is rejected, not vacuously green; a MISSING: env derives blocked; the probe distinguishes token-vs-network and the green run cleans up its edges; unit tests pass with the container stopped; the planted wrong value turns the de-tautologized test red.

9.3Ship it: integrate, accept, respondzero-tolerance exits▶

The tail of the pipeline is zero-tolerance by construction. bld-integration-verify replaces mocks with real services in wave order and exits only at "Mock remnants: ZERO"; each failure routes to the stage that owns it via a 4-way classifier. bld-acceptance applies six categories through a scope-aware matrix — mirrored verbatim between the skill doc and the Go config, with a drift test that fails when they disagree. bld-complete-work walks the status machine through its legal waypoints and fails loud on an illegal jump. And bld-qual-review-response carries the estate's bluntest verification lesson: success is the response body saying Recorded — never HTTP 200.

In the real system

The 4-way integration failure classifier: schema incompatibility → Stage 4 regen; behavioral assumption → Stage 1 contract enrichment; timing/ordering → Stage 1 or deployment config; single-responsibility defect → Stage 5 fix — and post-merge defects are fixed FORWARD on main, never reverted. bld-acceptance: a leaf needs zero matrix categories, a system needs all five; the Strategic Architect's SIGNIFICANT REGRET RISK hard-blocks until the DA resolves it. bld-complete-work: BUILT walks BUILT→IN_REVIEW→COMPLETE (acceptance was the review); BUILDING fails loud — no review ever ran. bld-qual-review-response: the feedback URL returns 200 to a GET with a self-submitting form that records NOTHING — the GET-only instruction survived from authoring until 2026-08-14, so every earlier headless run recorded zero verdicts while reporting success; "Recording your feedback" (present participle) vs "Recorded" (past tense) is the entire success discriminator. bld-smoke-cycle proves the pipes in ~5 minutes and never advances lifecycle: its artifact proof is git ls-remote returning a SHA equal to local HEAD.

Tasks

  1. Run a mini integration pass. Two Responsibilities, two waves, B consuming what A produces. Build B against a mock publisher; swap in real A; run the contract test from the graph's schema; then deliberately break one field in A's payload and classify the failure with the 4-way classifier before fixing it — the classification, not the fix, is the exercise.

  2. Encode the scope-class matrix twice, then test the drift. A Go map in your gate checker (leaf/service/system × 3 categories) AND the same table in your mini-acceptance skill doc — plus one test that parses the doc table and fails whenever it disagrees with the map. Run acceptance on a leaf node and verify only the always-on checks fire.

  3. Write /mini-complete-work. Gate first (check_gate(resp, acceptance_exit)), then the waypoint walk keyed on current status: IN_REVIEW → COMPLETE direct; BUILT → IN_REVIEW → COMPLETE in two calls; BUILDING → fail loud naming the missing review. You proved in week 2 the server rejects illegal jumps — this skill is the client that respects the map instead of fighting it.

  4. Build the Recorded-not-200 lesson. Add /feedback/:id/:verdict to your HTTP API: GET returns 200 with body "Recording your feedback"; POST returns 200 with body "Recorded". Write the disposition client that counts a verdict only on the POST body matching Recorded — and a test proving a GET-only client reports zero recorded while seeing nothing but 200s.

  5. Extract modal verbs into severities. A checker that greps your mini rules files for MUST / NEVER / DON'T lines and maps verb → severity (NEVER = RED blocking, MUST = YELLOW, RED when it touches auth or the spine). Wire one rule into mini-promote: implementing a decision still in Proposed blocks with a RED — only the human flips Proposed → Accepted.

Checkpoint

The broken payload lands in the right classifier bucket; the doc-vs-Go drift test goes red when you edit one side; BUILDING → COMPLETE fails in the skill AND the server; the GET-only client provably records nothing; and a Proposed-status implementation blocks RED.

Why it exists

Every mechanism in this lesson replaces a trust assumption with a check: "the merge is probably fine" → wave-ordered contract tests; "the reviewer probably looked" → matrix + drift test; "200 means it worked" → read the body. The pipeline's tail is where optimism is most expensive, because everything after it is production.

9.4Operating the fleet — and the atlasthe atlas▶

The last family keeps the pipeline honest over time: an FSM orchestrator that persists its state as graph nodes, a disk→graph sync with explicit conflict rules, drift detectors that join git history with graph governance, and four production operator skills that drive a deployed product surface under server-enforced four-eyes. Their shared shape: durable state plus gated seams — a mechanical read-only detection pass, a mutation that fires only through an explicit gate, and state persisted at every seam so a crashed run resumes instead of restarting.

In the real system

bld-orchestrate: create a StageExecution node BEFORE spawning each sub-agent, mark it after; "no gate check = no status advance"; a session active >4h with no evidence is stale — ask the human, never auto-re-run; a sub-agent that fails twice is escalated and the orchestrator moves on — one retry, then escalate. bld-sync-hosted's conflict rules R1–R5, first match wins: hosted-absent → apply; hosted >1.5× richer and local looks like a stub → SKIP (never overwrite richer content); byte-equal → skip; local richer → apply; both differ → ask the DA. Posting order matters: Decisions before Responsibilities, because lineage-edge targets must exist first — and a synced Decision is semantically dark until embed_document runs. bld-project-onboard's lie detector: if the wave plan puts everything in wave 1, the dependency graph is incomplete. The collections quartet (companion / expert / rule-analyst / rule-approver) shows skills as product surface: bootstrap hard gates (wrong-env token fails loud, zero-book stops the session), role gates (CREATOR / APPROVER checked server-side), and four-eyes the agent may not close — self_approval_blocked is a server refusal, surfaced verbatim, never retried around.

Tasks

  1. Give your pipeline an FSM memory. Add Run and StageExecution node types; /mini-orchestrate creates a StageExecution before each phase and marks it complete/failed after. Kill the session mid-run; verify the restart resumes from graph state — completed phases skipped, the interrupted one re-entered.

  2. Implement disk→graph sync with R1–R5. Seed one Decision whose graph body is 2× richer than its disk file and verify R2 skips it (never overwrite richer content); verify posting a Responsibility before its GOVERNED_BY target Decision fails, then succeeds when you order Decisions first; and index every synced node (_search) or watch it stay dark to your week-4 search.

  3. Enforce four-eyes. Stamp the submitter's id on each rule-ish draft node; make the approve MCP tool return self_approval_blocked when approver == submitter; have your mini-approver skill surface the refusal verbatim instead of retrying under another identity. The gate lives in the server — the skill only relays it.

  4. Work the atlas. Read the table below end to end — it is the whole estate. Pick THREE skills you did not build this week and write a one-paragraph mini design for each: its one permitted verb (or gate), its resume story, and the war story you'd tell a junior about why it exists.

Checkpoint — end of week 9

A killed mini-orchestrate run resumes from Run/StageExecution state; R2 provably protects richer graph content and mis-ordered posting provably fails; approve-your-own-draft returns self_approval_blocked from the server; and you can name, for any of the 57 rows, the one mechanism that skill exists to enforce.

Why it exists

The estate is not 57 clever prompts — it is a few hard-won mechanisms (reserve→redeem, verify-or-mark, bounded loops, one verb per skill, verify-personally, durable seams, four-eyes) instantiated wherever the pipeline touches reality. Learn the mechanisms and the catalog stops being memorization; meet a new skill and you already know its skeleton.
