Week 8 · Part IV — the skill estate

Skills I: idea → design

Week 7 taught the skill form — process as an executable document. Weeks 8–9 teach the skill estate: the ~57 bld-* skills that ARE the Nexus pipeline in daily operation. This week is the front half — the intake funnel, the challenge/promote spine, the design chain, and the findings machinery — and each lesson upgrades your own mini skills with the load-bearing mechanism the real skill exists to enforce. You are not cloning 57 files; you are extracting the dozen mechanisms they share.

  • Concept: reserve → redeem, verify-or-mark, bounded converge, one verb per skill
  • Build: /mini-backlog, /mini-challenge, /mini-scope-review, /mini-dedup, /mini-route
  • Upgrade: mini-ideate and mini-promote gain the real skills' failure-hardening
  • Doctrine: capture without fabrication; never trust an unverified graph write
8.1The intake funnel: capture without fabricationreserve → redeem▶

Ideas enter the pipeline through two doors. bld-ideate is the slow door: a six-forcing-question interview that refuses to mint a CIR until at least three have real answers. bld-backlog is the fast door: batch-capture at meeting speed, one confirmation for the whole batch — but each stub still clears the same server-side content gate, with every analytical section honestly stamped "Captured stub" instead of filled with invented analysis. Both doors share one id mechanism worth upgrading your allocator to: reserve → redeem. Reserve mints the canonical id with a TTL; redeem atomically creates the node while enforcing the content gate. The server owns the id algorithm — in the reserve → redeem path, a caller supplying its own id is rejected outright.

In the real system

bld-ideate (SKILL.md:101-107): NEVER create a CIR without ≥3 of the 6 forcing questions answered; reserve_decision_ids mints the id (server-derived slug + Crockford suffix, 7-day TTL) and redeem_decision_id enforces ≥500 chars + the literal <cir-quick-reference> block + every required ## section — passing id in properties fails with caller_supplied_id_forbidden. bld-backlog: at most ONE confirmation per batch, idempotent via a (session, nonce) pair, each stub tagged enrichment_status: "pending", and one failed item renders as a ✗ line without killing the batch. bld-narrative-author guards its Draft→Agreed flip with a server-side 4-check gate the skill may pre-flight but never simulate.

Tasks

  1. Split your allocator into reserve → redeem. ReserveDecisionID(ctx, docType, title) keeps the week-2 MERGE + ON-CREATE-marker statement but now creates a Reservation node ({id, project_id, expires_at}, TTL 7 days) instead of the Decision itself. RedeemDecisionID(ctx, id, content) checks the reservation exists and is unexpired, runs the content gate, creates the Decision node, and deletes the reservation — one transaction of intent. The week-7 initial-status rule moves with the create: redeem births a CIR at exploring, everything else at Proposed. Expose both as MCP tools; retire the single-step allocate_decision_id from mini-ideate's Phase 3 in favor of the pair (its step 4 read-back check stays — it now proves the redeem carried the status).

  2. Write the content gate. Redeem refuses when: content < 500 chars (content_too_thin), a required section is missing (missing_section: ## Riskiest assumption), or the caller passed an id inside the props payload (caller_supplied_id_forbidden — the reservation id is the only id). Structural completeness is a floor the server owns, not a convention the skill remembers.

  3. Build /mini-backlog. Feed it five one-line ideas. It must: parse them into discrete items, draft an honest-restatement stub per item (every analytical section literally reading "Captured stub — not yet analyzed"), ask ONE AskUserQuestion for the whole batch, reserve all five ids in a single call carrying an idempotency nonce, then redeem each — reporting a per-line ✓/✗ table. One deliberately-thin stub must ✗ without aborting its siblings.

  4. Prove the idempotency. Re-run the same batch with the same nonce: zero duplicate nodes. Then let a reservation expire (set a 5-second TTL for the test) and prove redeem fails cleanly with reservation_expired.

Checkpoint

Redeem rejects thin content, missing sections, caller-supplied ids, and expired reservations — each with its exact snake_case code; /mini-backlog captures 5 ideas on one confirmation, survives a re-run with zero duplicates, and renders ✗ for the sabotaged stub.

Why it exists

The stub discipline is the anti-fabrication doctrine applied to capture: a batch tool that "helpfully" fills in analysis invents evidence nobody gave it, and the graph can no longer tell a worked CIR from a guess. The real system's answer is structural: the same content gate for both doors, with honesty markers instead of padding — and enrichment_status so the backlog view never confuses the two.

8.2Challenge & promote, hardenedverify-or-mark▶

Between capture and authority sit three gatekeeper skills. bld-challenge stress-tests a CIR adversarially — and its reviewer is deliberately isolated: a subagent that receives only the CIR file path, no conversation history, so it cannot inherit your enthusiasm. bld-scope-review checks a promoted decision against the existing estate before any design begins. And bld-promote carries the mechanism this lesson is named for: verify-or-mark — a load-bearing graph write is never trusted on return; it is read back by the id the call returned, and if the read-back fails, a durable marker is written, the status flip is HELD, and the skill reports incomplete so a re-run is clean.

In the real system

bld-challenge: status flips to challenged at Step 0 before anything else; never validate without ≥2 implementation alternatives (one minimal-viable, one ideal); the isolated reviewer scores 5 dimensions, fixes loop max 3 times, and unresolved issues persist as a "Reviewer Concerns" section. bld-promote (verify-persisted.sh): read-back on a 0/0.25/0.5/1s backoff; on failure a marker JSON + best-effort Finding + PROMOTION INCOMPLETE, CIR flip held. Its spawn write-back refuses to guess on ambiguity — guessing by resemblance is what got PRs 39254/39326 abandoned. bld-scope-review + bld-strategic-design both mandate a TWO-pass prior-work search (semantic AND keyword) because the semantic index fails silent (Finding-large-synced-decision-YBYY); "none found" is only legal with the queries quoted verbatim. bld-author-decision's 7-box conflict gate exists because an ADR once went authored-to-accepted in 8 minutes over live authority nobody grepped for (Finding-adr-c2c-caching-WRZ0).

Tasks

  1. Write /mini-challenge (.claude/skills/mini-challenge/SKILL.md). Phase 1: flip the CIR exploring → challenged immediately. Phase 2: require ≥2 implementation alternatives in the CIR — one labeled "minimal viable", one "ideal architecture"; STOP if the author (you) can't produce two. Phase 3: dispatch a subagent whose entire input is the CIR file path — no chat context — scoring completeness, consistency, clarity, scope, feasibility 1–10 with one concrete issue each. Phase 4: fix and re-dispatch at most 3 times; whatever survives goes into a "Reviewer Concerns" section verbatim. Phase 5: verdict — update_status to validated, parked, or rejected, with the scores in the reason.

  2. Add verify-or-mark to mini-promote. After register_decision and after update_status: read the node back by the returned id on a 0 / 0.25 / 0.5 / 1s schedule. On a verified miss: write .minidde/promote-queue/<id>.json (what was attempted, when, observed error), print PROMOTION INCOMPLETE, and leave the CIR un-flipped. Then prove the recovery: with the marker present, re-run mini-promote and verify it completes cleanly with zero duplicate nodes — the MERGE from week 2 is what makes the retry safe.

  3. Write /mini-scope-review. Before a promoted decision may get a design brief: run BOTH semantic-search-like lookup (your _search Cypher from week 4) AND a keyword grep over docs/. The output must either cite the prior work it found or carry the literal line Prior work: none found (queries: "...", "...") — refuse to print "none found" without the queries echoed. Verdict is binary: CLEAR or BLOCKED — resolve N issues first.

  4. Gate direct authoring. Put a conflict checklist in front of register_decision for the no-CIR path: (a) grep docs/ for 3 tokens from the draft title, (b) query the graph for same-type decisions with overlapping _search hits, (c) classify every hit OVERLAP / RELATED / UNRELATED. The tool refuses registration while any box is unchecked — a partial gate means stop, never proceed.

Checkpoint

A CIR cannot reach validated without two alternatives and an isolated review; a simulated graph outage during mini-promote leaves a marker + an unflipped CIR, and the re-run completes without duplicates; scope-review refuses "none found" without quoted queries.

Why it exists

Every mechanism here is a scar. The isolated reviewer exists because a reviewer who shares your context shares your blind spots. Verify-or-mark exists because hosted writes failed silently mid-skill and the drift surfaced days later. The two-pass search exists because a null semantic result is indistinguishable from "no results". Distrust, mechanized.

8.3The design chain: one hand writes, bounded loops convergeconverge ledger▶

The design chain — bld-strategic-design → bld-autonomous-design → bld-design-review, with bld-design-update for governance drift — is one long instance of a single pattern: bounded evaluator–optimizer convergence. Exactly one authoring hand writes the document; independent reviewers fan out in parallel; all findings batch into ONE re-author dispatch per round; and the loop is hard-bounded — 3 rounds max, with the budget persisted in an on-disk ledger so it survives crashes and context clears. Every exit past the budget is an explicit escalation to the human, never a silent extra round.

In the real system

bld-autonomous-design's converge ledger: a ## Converge ledger table anchored by a whole-line <!-- converge-ledger:v1 --> marker (conformance: grep -cx == 1), append-only rows with SDD bytes before/after; a growth tripwire stops the loop when any round after the first grows the SDD by >50%, or at 500,000 bytes total — the byte ceiling guards every round, including the first. The war story: the first live v2 cycle died on unbounded converge — 81KB→136KB re-ingested across every lens until the token ceiling killed the run (Finding-first-v2-design-D8EE). bld-design-review's two structural gates: zero-open-items (the review cannot exit with any finding OPEN — no "accepted risk", no parking lot) and structurally-enforced deferrals (agents cannot create ExternalDependency nodes, so they cannot manufacture deferral reasons). Verdict enums are validated per-lens server-side — the strategic lens speaks ALIGNED / MINOR_RISK / SIGNIFICANT_REGRET_RISK, and "a strategic ACCEPTABLE is rejected". The scope-class two-hand split: the Designer authors the classification but holds no update_node; the session transcribes it verbatim but exercises no judgment — the hand that reads the gate cannot write the property.

Tasks

  1. Write /mini-brief. It queries your graph for the Accepted decisions governing the target Responsibility, then fills a dependency table where every upstream row carries a status (AVAILABLE / IN-DESIGN / NOT-STARTED) and a fallback-when-unavailable behavior. It refuses to register the brief Document while any cell is blank or "TBD", and creates GOVERNED_BY edges to each cited decision.

  2. Add the converge ledger to your design flow. A markdown file carrying the whole-line anchor <!-- converge-ledger:v1 -->; each review round appends a row with wc -c before/after. At startup, read rounds_used back from the ledger — refuse a 4th round, and hard-stop with an operator-facing message when a round grows the document by more than 50%. Kill the session between rounds and prove the budget survives.

  3. Build the zero-open-items gate server-side. A check_gate(resp, design_review_exit) that queries for Finding nodes with status OPEN attached to the Responsibility and blocks while any exist. No DEFERRED escape: your week-3 CheckDeferral (ExternalDependency + BLOCKS) is the only legal deferral, and you — the DA — are the only one who creates those nodes.

  4. Re-verify your 6.3 per-lens verdict scales — the design chain leans on them now: a strategic "ACCEPTABLE" must be rejected with a typed error naming ALIGNED | MINOR_RISK | SIGNIFICANT_REGRET_RISK, while skeptic/consistency/craftsman keep ACCEPTABLE | NEEDS_WORK | INADEQUATE. If your week-6 build validated the value sets but not per-lens, tighten it here. The lenses ask different questions; letting them share a vocabulary flattens the difference.

  5. Write the governance-delta script (the heart of bld-design-update): given the git ref of the last design approval, list decision records changed since it, query the Responsibility's GOVERNED_BY edges, and print a three-bucket report — changed-and-governed, changed-but-no-edge (missing governance), edge-to-superseded (stale governance). Empty delta → print "cosmetic only — no re-authoring required" and stop.

Checkpoint

The ledger survives a mid-loop kill and refuses round 4; a >50% growth round stops with a message, not another round; record_verdict rejects a strategic ACCEPTABLE; the delta script buckets a superseded-governor correctly; and no design exits review with an OPEN finding.

8.4The findings machinery: one verb per skillverb discipline▶

Eight skills govern what happens to a Finding after registration — intake, hygiene, routing, disposal, and the three responsibility-from-* exit ramps that turn findings and decisions back into buildable work. Their shared architecture is the sharpest discipline in the estate: each skill is permitted exactly one Finding-mutating verb and hard-prohibits the others. Dedup may only create_edge — never resolve. Route may only update_status(ROUTED) — never resolve. Dispose may only resolve_finding — never reject. Harvest may only register_finding — never confirm. A skill that can only do one thing to a Finding can be re-run, audited, and trusted; a skill that can do everything can silently do anything.

In the real system

bld-dedup-findings: TF-IDF cosine over OPEN findings — ≥0.85 auto-links DUPLICATE_OF (after checking BOTH edge directions), 0.45–0.85 queues for DA adjudication, and artifact overlap NEVER ranks: same-files-different-bug is labeled RELATED_DISTINCT, encoding the adjudicated failure of a predecessor that ranked by file overlap and got it wrong. bld-route-findings: "detector proposes, human disposes" — routed_by is the confirming human, never "system"; buckets must pre-exist (^[a-z-]+-findings-backlog-\d{4}$); the sent-ledger is the delivery idempotency. bld-findings-disposition is its earned-autonomy twin: the per-finding confirms collapse into autonomous phases ONLY after ≥2 consecutive manual passes with zero DA overrides — the checks stay, only the latency goes. bld-responsibility-from-finding bundles the DERIVED_FROM lineage edge into create_node, and one acceptance criterion is always mandatory: "Finding <id> can transition to RESOLVED upon completion". bld-transcript-harvest dedups by searching for exact citation substrings in the finding description — change one character of the template and every future run re-raises every Finding.

Tasks

  1. Write the verb table first. One row per mini finding skill you're about to build: skill → its one permitted write verb → the verbs it must refuse. Put it in a mini-WoW record. This table is the lesson; the code below just enforces it.

  2. Build /mini-dedup. Compute TF-IDF cosine over all OPEN findings (lowercase, strip stopwords, inverted index — ~40 lines of Go). Pairs ≥0.85: create DUPLICATE_OF after querying both edge directions (canonicalize the pair as (min id, max id)); add EdgeDuplicateOf = "DUPLICATE_OF" to week 1's edge constants + ValidEdgeTypes first, or CreateEdge will rightly refuse it. Pairs 0.45–0.85: print a review table, mutate nothing. Run it twice; assert zero new edges the second time. The skill never touches resolve_finding — by construction, a re-run can only skip.

  3. Add ROUTED and build /mini-route. Extend the Finding transition map with OPEN → ROUTED — and give it a way out: ROUTED → {RESOLVED}, with ResolveFinding relaxed to accept OPEN or ROUTED. Routing parks a finding in a bucket; it does not end its lifecycle — week 6's all_findings_terminal still counts ROUTED as open, so anything routed against a capstone Responsibility must be resolved before the week-10 gates. Add Bucket to ValidNodeTypes and pre-create one bucket node per capstone domain (booking-findings-backlog-2026…). The skill scans read-only, proposes routes, asks one confirmation per finding, then update_status(ROUTED) + DERIVED_FROM edge to the bucket — and when a proposed bucket doesn't exist, it records the residue and continues; it never creates buckets.

  4. Build /mini-resp-from-finding. Load a Finding; refuse if RESOLVED (offer "reopen first"); interview for purpose/scope with a "fold into parent instead" escape that stops the skill; create the Responsibility with the DERIVED_FROM edge bundled into CreateNodeWithEdges; force the mandatory acceptance criterion naming the Finding; then read the node back and fail unless the purpose is ≥100 chars and the edge exists — write-then-verify, never write-and-trust.

  5. Feel earned autonomy. Run /mini-route manually twice, overriding nothing. Then — and only then — write its fast-forward twin: same scan, same route test, a small route_exit gate declared first (scan_complete, routes_applied, delivery_complete — all evidence-bearing, or SubmitGateEvidence rightly refuses them), evidence submitted per phase, exactly ONE confirmation left (before "delivery"). The safety checks survive; the latency dies. If you had overridden even once, the collapse would not be earned yet.

Checkpoint — end of the funnel half

The verb table exists as a record; mini-dedup is idempotent and link-only; mini-route refuses to invent buckets and stamps you (not "system") as router; resp-from-finding's read-back gate fails on a thin purpose; and the fast-forward variant keeps exactly one human gate.

Why it exists

Findings are the graph's memory of what's wrong. Skills that mutate memory get the strictest discipline in the estate — because a "helpful" tool that resolves findings while deduplicating them, or routes while disposing, destroys the audit trail exactly where it matters most. One verb per skill is how the machinery stays legible at 3,000 findings.
